# 名古屋のフェチ・衣装交流に関するアンケート｜匿名Webアプリ

Google Apps ScriptのHTML Serviceで動く、匿名の市場調査アンケートWebアプリ。
Googleログイン・メールアドレスを一切要求せず、回答はGoogleスプレッドシートへ保存する。

> ## ⚠️ 設問・選択肢を変更する前に必ず読むこと
>
> 設問・選択肢の定義は **`Code.gs`（サーバー側検証・正本）と`Script.html`（クライアント側
> 表示・複製）の2箇所** に存在する。Apps ScriptはNode.jsのようなモジュール分割・import
> ができないため、この二重管理は構造上の制約であり、ここを1箇所に統合することはできない。
>
> **設問・選択肢を追加・変更・削除するときは、必ず`Code.gs`と`Script.html`の両方を
> 同時に更新し、コミット前に`tests/`のテスト（特に`compare_arrays.js`）を実行して
> 両者が完全一致することを確認すること。** 手順：
>
> ```sh
> cd community/gas/nagoya_fetish_survey_webapp/tests
> npm install   # 初回のみ
> npm test
> ```
>
> `compare_arrays.js`が`MISMATCH`を出した場合、選択肢の追加・削除・文言変更のどちらかを
> 片方のファイルにしか反映できていない。両ファイルの該当箇所を再度見比べて修正すること。

以前のバージョン（`community/gas/nagoya_fetish_survey_form_generator.gs`、Googleフォームを
自動生成する方式）は本バージョンで役目を終えたため削除した。理由は「同一ブラウザからの
意図的な繰り返し回答をブラウザ側の識別子で抑止する」仕組みがGoogleフォームでは組み込めず、
匿名性を保ったまま重複回答を抑止するには独自のWebアプリ（HTML Service）にする必要が
あったため。

## 調査ファネル（Issue #293）

PR #292時点は「参加障壁調査」を主目的とした単一フローの調査だったが、Issue #293以降は
以下のファネル型に再設計している。このアンケートは**イベント募集・参加申込・日程調整では
ない**（前半は一般的な嗜好調査、後半は条件に応じて関連企画について追加で聞く構成）。

```
STEP1（全回答者）
  Q1 都道府県 → Q2 愛知県内地域（愛知県選択時のみ） → Q3 年代
STEP1A（全回答者・分析の主）
  Q4 興味のある衣装・服装・キャラクター表現（複数回答・分析の主）
  Q5 特に好きなジャンルを1つ選ぶとしたら（Q4選択項目のみ候補・補助指標）
  Q6 その衣装・服装とどう関わりたいか（複数回答）
    │
    ├─ ユニフォーム系ゲート該当（スポーツ・ユニフォーム系／学校制服／作業着／職業制服のいずれか）
    │    STEP2  Q7 SNBC認知 → Q8 SNBCユニ会企画への興味（はい/いいえ/どちらともいえない）
    │      └─ Q8=はい → STEP3（PR #292由来の深掘り一式を再利用）
    │
    └─ 「スーツ」選択（ユニフォーム系ゲートとは別条件）
         STEP2B  S1〜S4（スーツ専用の短い嗜好設問）
           └─ S4=はい → STEP3の深掘り一式を再利用（二重には聞かない）

  両方に該当する回答者は、STEP2（該当すればSTEP3まで）を先に完走してから
  STEP2Bに進む（事業上の優先データはSNBC参加意向のため、疲労が溜まる前に確実に取得する）。
```

- **分析の主はQ4（`interest_categories`）の複数回答**。Q5（`primary_interest_category`）は
  補助指標として使い、回答者を1ジャンルに固定して解釈しない。
- 「あなたは○○フェチですか？」という自己ラベル質問は使わず、代わりに「何に惹かれるか／
  自分で着たいか／人が着ているのを見たいか／撮る・撮られる側として関わりたいか」を取る
  （`engagement_preferences`）。
- SNBC関連の深掘りは、ユニフォーム系に関心があり、かつSNBC企画に興味を示した回答者
  （`snbc_interest = 'はい'`）だけに出す。スーツ系は専用の短いSTEPを持つが、深掘り本体は
  PR #292の共通設問（頻度・料金・人数・参加形式・障壁・温度感・仮定参加意向など）を再利用する。
- PR #292で実装した参加障壁・温度感・「2人だけ〜大人数」・申込ギャップ等の観点は削除していない。

### `completion_stage`（状態遷移）

1回答者につき、到達した最終地点をただ1つ表す値。実行順序が「ユニフォーム系ゲート
（該当すればSTEP3まで）→スーツSTEP2B」で固定のため、スーツを選んだ回答者は常に
`suit_interest`が最終地点になる（ユニフォーム系側の到達地点を示すフィールドは
両方保持してよいが、`completion_stage`自体は1値のみ）。

| stage | 意味 |
|---|---|
| `no_gate_reached` | STEP1A止まり（ユニフォーム系・スーツいずれのゲートにも非該当） |
| `snbc_not_interested` | ユニ系ゲート該当・Q8=いいえ |
| `snbc_uncertain` | ユニ系ゲート該当・Q8=どちらともいえない |
| `snbc_deep_dive` | ユニ系ゲート該当・Q8=はい・STEP3完走 |
| `suit_interest` | Q4でスーツ選択・S1〜S4回答済み（ユニフォーム系にも該当する場合は最終地点として優先） |

クライアントから送られた`completion_stage`・`survey_path`は無条件に信用せず、`Code.gs`の
`validateAnswers_`が回答内容（`interest_categories`の内容・`snbc_interest`等）から
サーバー側で独立に再計算し、一致しない場合は送信を拒否する。

### `clothing_interests` と `interest_categories` の関係（重要）

`interest_categories`は`clothing_interests`（PR #292実装済み・12択）の**後継ではなく、
別列として新設**したものである。

- 旧`clothing_interests`列・旧12択の過去回答は一切変更しない（読み取り専用の参考値として保持）。
- 新規回答からは`interest_categories`（新カテゴリ、22択+その他）にのみ保存する。旧列には
  新規回答時は値を入れない（空文字列のまま）。
- 理由：旧「スイムウェア」が新「競パン」「水泳・競泳ウェア（競パン以外）」に分岐するなど、
  旧→新の選択肢は機械的に対応付けられないため、遡及マッピングによる過去データの書き換え・
  推測補完は行わない。
- 集計（`集計_衣装カテゴリ`等）は新列`interest_categories`を基準に作り直した。旧
  `clothing_interests`基準の集計は`集計_服装（旧12択・参考値）`として最低限だけ残し、
  タイトルに「（旧12択・参考値）」と明記して新集計と混同しないようにしている。

## ファイル構成

| ファイル | 役割 |
|---|---|
| `Code.gs` | サーバー側ロジック。UUIDのハッシュ化・重複判定・保存・集計シート生成。設問の選択肢定義（正本）もここにある。 |
| `Index.html` | ページの骨組み（読み込み中／回答済み／送信済み／フォーム、の各状態パネル）。 |

| `Script.html` | クライアント側ロジック。設問定義（Code.gsと同じ内容を保持。両方を同時に更新すること）、UUID/Cookie処理、フォーム描画・検証・送信。 |

## デプロイ手順

1. **Apps Scriptプロジェクト作成**：[script.google.com](https://script.google.com) で新規スタンドアロンプロジェクトを作成し、上記4ファイルを同じファイル名で貼り付ける（`.html`拡張子のファイルとして追加すること）。
2. **スプレッドシートID設定方法**：回答保存用のGoogleスプレッドシートを別途1つ新規作成し、URL中の `/d/` と `/edit` の間の文字列（スプレッドシートID）をコピーする。
3. **Script Properties**：Apps Scriptエディタ左側の「プロジェクトの設定」（歯車アイコン）→「スクリプト プロパティ」で、キー `SPREADSHEET_ID` に手順2のIDを設定する（`SERVER_SALT` は未設定でよい。初回アクセス時に自動生成される）。
4. 関数選択で `initializeAll` を実行する（初回は権限承認が必要。下記参照）。`responses`シートと集計用の`集計_*`シート群が作成される。
5. **Web Appとしてデプロイ**：「デプロイ」→「新しいデプロイ」→種類「ウェブアプリ」。
6. **実行ユーザー・アクセス**：実行ユーザーは「自分」、アクセスできるユーザーは「全員」（リンクを知っている全員相当。Googleアカウントが必要な設定は選ばない）。
7. **URL取得**：発行された `/exec` で終わるURLがアンケートの回答用URL。SNB/SNBCサイトからはこのURLへリンクを貼るだけでよい（このリポジトリ側の実装は不要）。
8. **動作確認**：URLを開いてフォームが表示されること、1件テスト回答を送信してスプレッドシートに反映されること、同じブラウザで再訪すると「回答済み」表示になることを確認する。

設問・選択肢を変更した場合は、`Code.gs`と`Script.html`の両方を更新したうえで再デプロイ（同じデプロイの「新しいバージョン」を選択）しないと本番URLへ反映されない。

## 初回権限承認

`initializeAll`の初回実行時、またはWebアプリへの初回アクセス時にGoogleの承認ダイアログが出る。
「権限を確認」→アカウント選択→「このアプリは確認されていません」と出たら「詳細」→
「（プロジェクト名）に移動」→「許可」の順に進める（自作の未公開スクリプトのため想定通りの警告）。
要求される権限はスプレッドシートの読み書きとWebアプリの実行のみ。

## 既知の限界

`Code.gs`の末尾コメントを参照。要点は以下の3点。

- Cookie削除・localStorage削除・シークレットモード・別ブラウザ・別端末を使われた場合、新しいUUIDが発行され「別人からの新しい回答」として保存される（意図的な突破は防げない設計）。
- IPアドレス・User-Agent・ブラウザフィンガープリント等は一切収集していない（匿名性優先の設計判断）。
- Apps ScriptのWebアプリは実体としてgoogleusercontent.comのiframe内に埋め込まれて配信されるため、Cookieがブラウザによって「サードパーティCookie」として扱われ、ブロック・分離される場合がある（特にSafari/iOS）。localStorageを主、Cookieを補助的なフォールバックとする設計はこれを踏まえたもの。
